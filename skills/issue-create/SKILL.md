課題や要望を，GitHub issueとして起票する．この時点ではソース調査は行わない (調査はissue対応時に行う)．

## コマンド実行の規定

この規定は，スキル本文に記載されたコマンドの実行と，手順を進める中で実行側が自分で組み立てるコマンドの両方に適用する．

- スキル本文に記載されたコマンドは，記載されたままの形で実行する．オプションの追加・削除，引数の順序変更，コマンドに渡す文言をいったんシェル変数に格納してから参照する形への書き換え，末尾に`&& echo ...`をつないで成否を確認する形への書き換えなど，記載と異なる形にしない．成否確認や可読性のための書き換えも同様に行わない．実行許可の判定はコマンド全体に対して行われるため，わずかな書き換えでも許可設定と一致せず，不要な確認プロンプトで作業が中断される
- 1回のBash呼び出しで実行するコマンドは1つとし，`&&`・`;`・`|`で複数のコマンドをつながない(スキル本文にその形で記載されている場合を除く)．1つのコードブロックに複数行のコマンドが並んでいる場合も，まとめて1回で実行せず，行ごとに1回のBash呼び出しに分ける．どの行を実行するかは本文の説明に従い，択一の選択肢として複数のコマンドが並んでいる場合は該当するものだけを実行する．調査時に出力を絞り込みたい場合は，パイプでつなぐのではなく`Grep`・`Read`ツールを使うか，コマンド自身のオプションで絞る．`> <ファイル>`によるファイル出力は，スキル本文に記載されているとおりに用いてよい
- `cd`については上記の例外を認めず，常に単独のBash呼び出しにする．`cd <パス> && <コマンド>`のような複合コマンドにはせず，`cd <パス>`単独の呼び出しと，その後の素のコマンド呼び出しに分ける．作業ディレクトリはworktree内にとどまる限りツール呼び出しをまたいで保持されるが，worktreeの外にあるディレクトリへは`cd`しても次のBash呼び出しには維持されない
- 次のものは改変に当たらない
  - `<番号>`のようなプレースホルダを実際の値に置き換えること
  - `[...]`で任意と示されたオプションを付ける，または付けないこと
  - 「〜を依頼する文言」のように，スキル本文が渡すべき内容を説明しているだけの箇所を，実際の文言に書き起こすこと(ただし文言はコマンドラインに直接書き，シェル変数への格納や別ファイルへの書き出しを経由しない．改行を含む長い本文は，ヒアドキュメントでコマンドライン中に直接書いてよい)
  - スキル本文の説明が指示している変形(`git -C <絶対パス>`形式への変換，`--head`の明示，`--add-dir`に指定するディレクトリの読み替えなど)
- 記載どおりのコマンドでは目的を達成できない場合は，黙って改変せず，記載どおりでは達成できない理由と実際に実行するコマンドをユーザーに説明した上で，回避となるコマンドを実行する(ユーザーの応答は待たずに作業を進めてよい)．人間が介在しない非対話的な実行の場合は，同じ説明を出力に含める

## 手順

1. issueにしたい内容を話し合い詳細にする
2. タイトルと本文をドラフトする．タイトルは，追加してほしい機能または発生している不具合の概要が分かるような文章にする．本文には以下を含める
   - 課題: 修正を依頼する動機．機能追加なら，追加したい機能がない現状，不便・不満に感じている事．不具合なら発生している事象
   - ゴール: 上記課題を解決して実現したいこと．機能追加なら，具体的にどのような機能が欲しいのか．不具合なら理想の動作
   - 補足: 何かあれば．不具合の場合，再現条件を明示する必要があるならここに記載
3. 対象リポジトリを判定する
   - 内容が単一リポジトリに閉じるなら，そのリポジトリにissueを作成する
   - 複数リポジトリにまたがる可能性がある場合は，1つのissueで複数リポジトリをまとめて扱うか，リポジトリごとに分けるかをユーザーに確認する
   - 特定のリポジトリが主担当と判断できない，全リポジトリに影響する内容の場合は`for-pynthesis-skills`リポジトリに起票する(複数リポジトリに影響する場合でも，メインで修正するリポジトリが決まっているならそちらに起票する)
4. ドラフトを提示し，承認を得てから作成する (GitHub上に公開される操作のため，作成前に必ず確認する)．**ただし，このスキルを起動したプロンプト自身が「`issue-resolve`の自動レビューループから非対話的に起動している (人間が介在しない)」と明示している場合のみ**，この承認手順を省略してそのまま作成してよい．この場合は深い検証は不要で，「〜の可能性がある」程度の疑いでも起票してよい (推測であることが分かる書き方にする点は変わらない)．非対話起動であることが明示されていない限り，通常どおり人間の承認を得る
5. `gh issue create --repo <owner>/<repo> --title "<タイトル>" --body "<本文>"` で作成する
6. 作成したissueのURLを報告する (手順4の例外を適用した場合は，レビュー結果の出力に含める)

## 注意

- issue本文は日本語で記述し，句読点は「，」「．」を使う
- 事実 (確認済みの挙動・再現手順など) と推測 (未検証の仮説) を区別して書く．推測は「〜と思われる」「〜ではないか」のように，推測であることが分かる書き方にする
- 未承認のまま`gh issue create`を実行しない．例外は，起動プロンプト自身が非対話的な自動レビューループからの起動であることを明示している場合のみ (手順4参照)
