# 概要

GitHub issueへの対応 (調査・ブランチ作成・修正・PR作成) を行う．粒度は1issue=1回の実行．

# コマンド実行の規定

この規定は，スキル本文に記載されたコマンドの実行と，手順を進める中で実行側が自分で組み立てるコマンドの両方に適用する．

- スキル本文に記載されたコマンドは，記載されたままの形で実行する．オプションの追加・削除，引数の順序変更，コマンドに渡す文言をいったんシェル変数に格納してから参照する形への書き換え，末尾に`&& echo ...`をつないで成否を確認する形への書き換えなど，記載と異なる形にしない．成否確認や可読性のための書き換えも同様に行わない．実行許可の判定はコマンド全体に対して行われるため，わずかな書き換えでも許可設定と一致せず，不要な確認プロンプトで作業が中断される
- 1回のBash呼び出しで実行するコマンドは1つとし，`&&`・`;`・`|`で複数のコマンドをつながない(スキル本文にその形で記載されている場合を除く)．1つのコードブロックに複数行のコマンドが並んでいる場合も，まとめて1回で実行せず，行ごとに1回のBash呼び出しに分ける．どの行を実行するかは本文の説明に従い，択一の選択肢として複数のコマンドが並んでいる場合は該当するものだけを実行する．1行実行するごとに結果を確認し，失敗していれば以降の行を実行せず原因を解消する(互いに独立したコマンドを本文の指示に従って並列に実行する場合を除く)．実行側が自分で組み立てるコマンドで出力を絞り込みたい場合は，パイプでつなぐのではなく`Grep`・`Read`ツールを使うか，コマンド自身のオプションで絞る(本文に記載されたコマンドは，出力が大きくてもオプションを足さずそのまま実行する)．`> <ファイル>`によるファイル出力は，本文が`>`を用いている用法(レビュー結果をファイルに出力する場合)と同じ目的であれば，本文に記載のないコマンドでも用いてよい
- `cd`については上記の例外を認めず，常に単独のBash呼び出しにする．`cd <パス> && <コマンド>`のような複合コマンドにはせず，`cd <パス>`単独の呼び出しと，その後の素のコマンド呼び出しに分ける．作業ディレクトリはworktree内にとどまる限りツール呼び出しをまたいで保持されるが，worktreeの外にあるディレクトリへは`cd`しても次のBash呼び出しには維持されない
- 次のものは改変に当たらず，上記の各項目より優先する
  - `<番号>`のようなプレースホルダを実際の値に置き換えること
  - `[...]`で囲まれたオプションを，本文が示す条件に従って付ける，または付けないこと(自由に選べるという意味ではない)
  - 「〜を依頼する文言」のように，スキル本文が渡すべき内容を説明しているだけの箇所を，実際の文言に書き起こすこと
  - コミットメッセージ・issue本文・PRの本文やコメント・`claude -p`に渡すレビュー依頼文言など，改行を含む文字列を引数として渡す際に，本文の`-m "<コミットメッセージ>"`のような単純なクォートを`-m "$(cat <<'EOF' … EOF)"`に組み替えること(オプションの書式が`-f body=`や`-- "<文言>"`であっても同様．ヒアドキュメントとコマンド置換でコマンドライン中に直接書く形であり，複数コマンドの連結にも当たらない．いったんシェル変数に格納したり，別ファイルに書き出して読み込ませたりはしない)
  - スキル本文の説明が指示している変形(`git -C <絶対パス>`形式への変換，`--head`の明示，`--add-dir`に指定するディレクトリの読み替えなど)
- 記載どおりのコマンドでは目的を達成できない場合は，黙って改変せず，記載どおりでは達成できない理由と実際に実行するコマンドをユーザーに説明した上で，回避となるコマンドを実行する(ユーザーの応答は待たずに作業を進めてよい．ただし回避となるコマンドが破壊的操作やGitHub上に公開される操作に当たる場合は，本文の規定に従って実行前に承認を得る)．出力が大きすぎて作業を続けられない場合も，同じ扱いとする．人間が介在しない非対話的な実行の場合は，同じ説明を出力に含める

# 手順

## 1. issue内容の確認

```
gh issue view <番号> --repo tt-and-tk/<repo>
```

## 2. 調査

原因調査を行い，影響範囲 (対象リポジトリ・対象ファイル) を特定する．issue本文中に推測が書かれている場合は，事実かどうかをここで検証する．

`for-pynthesis-skills`以外のプロジェクトで開いたセッションで，`specification`を除く影響リポジトリが複数あると判明した場合は，この時点で次のどちらで進めるかをユーザーに選んでもらう．

- 各リポジトリのプロジェクトで個別に実行する: 各リポジトリの許可設定・プロジェクト固有のスキルのもとで作業できる．ただし実行がリポジトリごとの別セッションに分かれる
- `for-pynthesis-skills`のプロジェクトで開き直し，1セッションでまとめて実行する: リポジトリをまたぐ修正を1つの方針のもとで揃えられる．ただし他のリポジトリはcloneで扱うため，そのリポジトリの許可設定・プロジェクト固有のスキルは効かない．開き直した新しいセッションで手順1から実行し直す

## 3. 修正方針の承認

調査結果と修正方針を固めたら，ユーザーに提示する前に`claude -p`による設計レビューを行う．対象は方針テキストだけでなく，関連する既存仕様・ソース(矛盾がないか判断するのに必要な範囲)も含める．技術的なツール制限は付与せず，プロンプト文言で「読み取りのみを行い，修正は行わないこと」を指示する．方針の妥当性という難しい判断を求めるため，`--model fable`を指定する．ただし実行側自身が`fable`の場合は，自己レビューを避けるため`--model opus`を指定する(実行側のモデルの判定方法は自動レビューループの「レビューに使うモデル」に従う)．関連ファイルが別リポジトリ(別プロジェクト)にある場合は，`--add-dir <ディレクトリ>`でそのディレクトリへの読み取りアクセスを明示的に付与する(この時点では4.1のcloneをまだ作っていないため，各リポジトリの既存のローカルディレクトリを指定する)．

```
claude -p --model <モデル> [--add-dir <別リポジトリのパス>...] -- "issue #<番号>(tt-and-tk/<repo>)への対応方針(設計)のレビューを依頼する文言．方針の内容と，判断に必要な関連ファイル<パス>を提示し，既存仕様との矛盾・考慮漏れがないか確認してもらう．必要なら'gh issue view'でissue詳細を取得してよいことを伝える．読み取りのみ行い，修正は行わないことを明記する"
```

レビュー指摘のうち対応すべきと判断したものは，ユーザーに提示する前に方針へ反映する(対応方針は末尾「レビュー指摘への向き合い方」を参照)．反論する場合，設計段階ではまだコミットが存在しないため記録先を設けず，同じ指摘が再度出た場合に「以前この理由で対応しなかった」旨を次のレビュー依頼時のプロンプトに含めればよい．

その上で，調査結果と(設計レビューを反映済みの)修正方針をユーザーに提示し，承認を得る．**これが実装前の最後の確認ポイント**であり，承認後は手順4を人間の追加確認なしに連続して実行する(4.2で実機での動作確認を行う場合のみ，そこで一度止まる)．  
ここでは，特に聞かれない限り具体的なソース内容を提示する必要はない．ソースのうち，どの仕事をする部分をどのように修正するかを提示できれば十分．  

## 4. リポジトリごとの実装〜PR作成

影響リポジトリごとに以下を行う．**原則として，1つのセッションで編集するのはセッションを開いたプロジェクトのリポジトリ(本スキル開始時の作業ディレクトリが属するリポジトリ．以降セッションのリポジトリと呼ぶ)だけとし，複数リポジトリを串刺しに編集しない．**セッションのリポジトリでの対応が完了したら，他の影響リポジトリについては，対象リポジトリと該当issue番号を明示した上で，そのリポジトリのプロジェクトで本スキルを実行するようユーザーに依頼する(このセッションから直接他リポジトリを操作しない)．issue自体は1つのままでよく，実装の実行単位だけをリポジトリごとに分ける．

次の例外に当たるリポジトリは，セッションのリポジトリ以外であっても，4.1の疑似隔離(clone)を用いてこのセッションから直接ブランチ作成・ファイル操作・PR作成を行ってよい(別セッションへの依頼は不要)．

- **`for-pynthesis-skills`のプロジェクトで開いたセッションで，影響リポジトリが複数ある場合の全影響リポジトリ:** `for-pynthesis-skills`は全リポジトリに影響するissueの受け皿を兼ねるため，リポジトリをまたぐ修正を1セッションでまとめて扱ってよい．ただし，4.2の実機での動作確認を要する`qurge`の修正は，clone先のパスが深くなりVivadoで扱いづらいため，`qurge`のプロジェクトで行う．影響リポジトリが1つだけの場合はこの例外に当たらない(cloneではそのリポジトリの許可設定・プロジェクト固有のスキルが効かないため，単独の修正はそのリポジトリのプロジェクトで行う)
- **`specification`:** Claude Codeプロジェクトを持たない(非プロジェクトという既存設計のため)ため，どのプロジェクトで開いたセッションからでも扱ってよい

**セッションのリポジトリが修正対象に含まれない場合:** 修正対象がすべて例外で扱うリポジトリの場合である．例えば影響リポジトリが`specification`単独の場合がこれに当たる．`specification`はClaude Codeプロジェクトを持たず実行主体として選べないため，起動する時点で分かっていれば，全リポジトリに影響するissueの受け皿を兼ねる`for-pynthesis-skills`のプロジェクトから本スキルを実行する．他のプロジェクトで調査中に判明した場合は，開き直さずそのまま続けてよい．いずれの場合も，セッションを開いたプロジェクトは実行主体であり，修正対象とは別物である．この場合は4.1の`EnterWorktree`は行わず，修正対象はすべて4.1の疑似隔離で扱う．4.1のclone先は`pwd`で確認した作業中のローカルリポジトリ内(`<作業中のローカルリポジトリ>/.worktrees/`配下)とする規定になっているが，この場合`pwd`はセッション開始時点のローカルリポジトリを指すため，追加の準備なしにそのまま適用できる(`EnterWorktree`によるネストを介さない点のみ通常のケースと異なる)．

### 4.1 作業場所の準備

セッションのリポジトリは，`EnterWorktree`(name: `fix/issue-<番号>-<内容を表す短い語句>`)で専用の作業ディレクトリとブランチを作成してから作業する．`EnterWorktree`はブランチ作成まで一体で行うため，**別途`git checkout -b`でブランチを作る必要はない**．**セッションのリポジトリと，疑似隔離で扱うリポジトリ(下記)の両方がこのセッションでの対象になる場合，cloneする作業より先にこの`EnterWorktree`を実行する．** 順序を誤ると，先にcloneしたリポジトリの作業ディレクトリが，後から実行する`EnterWorktree`による隔離範囲の外側になり，以降のgit操作がブロックされる．

**`EnterWorktree`が作るブランチ名は，渡した`name`に`worktree-`を接頭辞として付与し，`/`を`+`に置換した`worktree-fix+issue-<番号>-<内容を表す短い語句>`になる．** 以降の手順でブランチ名を書く場合は，この形式をそのまま用いる．

**手順4冒頭の例外で扱う，セッションのリポジトリ以外のリポジトリには`EnterWorktree`が使えない．** `EnterWorktree`は現在のリポジトリまたはそこにネストしたリポジトリにしか使えず，それらのリポジトリは現在のリポジトリと兄弟関係にあるためである．代わりに，そのリポジトリをリモートから直接cloneして疑似的な隔離を作る(以降これを**疑似隔離**と呼ぶ)．**GitHub上のリモートから取得した独立した作業用コピーであり，そのリポジトリのローカルディレクトリとは無関係である．** clone先は，サンドボックスの書き込み制限により兄弟の場所には作れないため，`pwd`で確認した作業中のローカルリポジトリ内(`<作業中のローカルリポジトリ>/.worktrees/`配下)とする．

**clone先の基準に`pwd`の実行結果を使う理由:** 疑似隔離のcloneを，セッションのリポジトリの`EnterWorktree`のworktree内に作りたいためである．上記のとおり`EnterWorktree`を先に実行していれば，`pwd`は自動的にそのworktree配下を指すため，疑似隔離のcloneも自動的にworktree内にネストする．

```
pwd
gh repo clone tt-and-tk/<リポジトリ名> "<作業中のローカルリポジトリ>/.worktrees/<リポジトリ名>-fix-issue-<番号>-<内容を表す短い語句>"
git -C "<作業中のローカルリポジトリ>/.worktrees/<リポジトリ名>-fix-issue-<番号>-<内容を表す短い語句>" checkout -b fix/issue-<番号>-<内容を表す短い語句>
```

各プロジェクトの`.gitignore`は`.worktrees/`を除外済みである前提とする(未対応の場合は別issueで一括対応する)．`EnterWorktree`のworktree配下にネストする場合も，そのworktreeは対象リポジトリと同じ内容をチェックアウトしているため，同じ`.gitignore`が有効である．

**疑似隔離で扱うリポジトリに限り，以降の手順でそのリポジトリに対して実行するgitコマンドは，すべて`git -C <cloneしたディレクトリの絶対パス> ...`の形式で実行する．** `add`・`commit`・`push`だけでなく，`diff`・`status`・`log`・`rev-parse`など読み取り系も含めた全てが対象である．cloneしただけではセッションの作業ディレクトリは切り替わらず，clone先はセッションの作業ディレクトリの外にあるため`cd`しても次のBash呼び出しには維持されない．形式を省くと現在のプロジェクトを操作してしまう．`EnterWorktree`を使うセッションのリポジトリは，セッションの作業ディレクトリがその中にあるため素の形式でよい．

### 4.2 修正

手順3で承認された方針に基づいて修正を行う．

疑似隔離で作業している場合，**編集するのはclone先のファイルであり，元のローカルディレクトリのファイルではない．** 手順3の設計レビューでは元のローカルディレクトリを読み取り対象にしているため，そのパスのまま編集に入ると取り違える．元を編集すると，clone先には変更が無いまま空のコミット・PRになり，かつ元のローカルディレクトリに意図しない変更が残る．

**Vivadoプロジェクトを含むリポジトリ(`qurge`)の場合**，合成・ビットストリーム生成は毎回行う必要はなく，実機での動作確認が必要な場合にのみ行う．要否は手順3の修正方針に含めてユーザーの承認を得ておく．

実行には長時間かかりBashツールのタイムアウトに収まらないため，スキルからは実行せず，作業ディレクトリのパスを伝えてユーザーに実施を依頼し，結果を受け取るまで待つ(手順3の承認とは別の，人間の確認を要する箇所である)．合成の中間生成物はGit管理外で作業ディレクトリには存在しないため，最初の合成には時間がかかる．作業ディレクトリのパスからプロジェクトを開くこと自体に制約はない(プロジェクトファイルはソースの位置を相対的に持つため，どのディレクトリでも開ける)．

確認の結果ハードウェアの修正が必要になった場合は，この手順に戻って修正する．手順4.4・4.5でハードウェアを修正した場合も同様に扱う．実機での確認はマージ前に完了させる(マージ後はPRもブランチも閉じており，修正が必要になっても戻る先が無い)．

### 4.3 コミット・push・PR作成

```
git add <変更したファイル>
git commit -m "<コミットメッセージ>"
git push -u origin HEAD
gh pr create --repo tt-and-tk/<repo> --title "<タイトル>" --body "<本文>" [--draft]
```

push先は，ブランチ名を書かず`HEAD`で現在のブランチを指す(`EnterWorktree`が作るブランチ名は`name`と一致しないため，名前を書くと存在しない別のブランチを新規に作ってしまう)．

PR作成時の`--body`に，closeキーワード (`Closes tt-and-tk/<repo>#番号`) またはリンクのみ (`Related to tt-and-tk/<repo>#番号`) を含める．closeキーワードは1issueにつき1箇所のPRのみに付与する (issueが存在するリポジトリのPR，またはユーザーが指定したPR．issueが存在するリポジトリにPRを作らない場合は付与先が無くissueが閉じないため，手順3の方針提示時にどのPRに付与するかをユーザーに確認しておく)．それ以外のリポジトリのPRは`Related to tt-and-tk/<repo>#番号`のみを記載する．  

**`--draft`は，closeキーワードを持つPRにのみ付ける．** マージするとissueが閉じるPRであることを一目で分かるようにするための運用．closeキーワードを持たない(`Related to`のみの)PRはissueを閉じないため，通常のPR(Ready)として作成する．  

**疑似隔離(4.1でcloneしたディレクトリ)で作業している場合**，上記のgitコマンドは4.1の規定に従って`git -C <cloneしたディレクトリの絶対パス> ...`の形式で実行する．あわせて`gh pr create`には`--head fix/issue-<番号>-<内容を表す短い語句>`を明示してpush先ブランチを指定する(`gh`はセッションのカレントディレクトリからブランチを判定するため，明示しないと別のブランチを指す)．

### 4.4 自動レビューループ

`claude -p`によるレビューを行い，修正すべきと判断した指摘がなくなるまで，人間の確認なしに修正・再レビューを繰り返す．変更内容のうち説明が必要な箇所は，PRへのコメントまたはコミットメッセージで補足する．  

#### 観点

レビューは観点ごとに`claude -p`の呼び出しを分ける．代表的な観点は以下の通りで，修正内容に応じて他の観点を追加してもよい．**太字が観点名，続く括弧がその観点を行う場面，コロンより後がレビュー依頼文言にそのまま用いる定義**である．

- **全体レビュー**(必須): 対象ファイル全体を読み，記述の矛盾・抜け漏れ・不具合の有無を確認してください
- **新規読者理解可能性レビュー**(必須): 次の3つに該当する箇所を，ファイル名と該当箇所が分かる形ですべて列挙してください
    - 既存の記述の修正ではなく，記述が追加されているだけの箇所(新規追加ファイルは除く)
    - 将来変わる可能性が高いものを名指ししている箇所(行番号・見出し番号・変数名・関数名など)
    - 将来項目が増えた場合に追記が必要になる列挙(例外の説明に含まれる機能の列挙など)
- **コーディング規約レビュー**(必須): ユーザー共通の`~/.claude/CLAUDE.md`に記載されたコーディング規約(文章・コメントの書き方，情報の残し方など)に従っていないファイル中の記述を，ファイル名と該当箇所が分かる形ですべて列挙してください．コミットメッセージなどファイル以外の情報は対象外です
- **テストコードの網羅性レビュー**(機能の追加・変更を伴う修正の場合): 仕様書やソースの内容を踏まえ，追加・変更した機能について，正常系・異常系を含め想定されるさまざまな使われ方に対してテストコードに考慮漏れがないかを確認してください
- **整合性レビュー**(既存ドキュメント・関連ファイルに影響する変更を行った場合や，仕様変更・新機能の追加によって過去の制限が撤廃された場合など，関連箇所の更新漏れが起きやすい状況): `specification`等の既存ドキュメント，同一リポジトリ内の他ファイル，他リポジトリの関連ファイル，あるいは同一ファイル内の過去の記述との間に，矛盾や対応漏れがないかを確認してください
- **可読性・保守性レビュー**(ソースの追加・変更量が多い場合): 命名・重複・複雑度など，読みやすさ・保守しやすさの観点から確認してください
- **パフォーマンスレビュー**(パフォーマンスに影響しうる変更の場合): 不要な処理・非効率な実装がないかを確認してください
- **ハードウェア記述レビュー**(ハードウェア記述(SystemVerilog等)を変更した場合): 合成可能な書き方になっているか，動作タイミング・使用リソースに問題がないかを確認してください

#### 観点ごとの実施条件

どの観点で何回`claude -p`を呼ぶかは，上記の場面と下表の実施条件の範囲で実行側(このスキルを実行しているセッション)の判断に委ねる．

| | 全体レビュー | 新規読者理解可能性レビュー・コーディング規約レビュー | 上記以外の観点 |
|:-|:-|:-|:-|
| 実施 | このリポジトリでの4.4を通じて1回だけ(4.5での再実行を含め2回目以降は行わない) | そのPRのコミット1つにつき1回．未実施のコミットを残さない(4.5での人間レビュー対応後に追加したコミットも同様)．ただし，これらの観点の指摘に対応したコミットは対象外とし，判別できるようコミットメッセージに観点名を含める | 任意 |
| 回数上限 | 1回 | なし | 2〜5回 |
| レビュー対象 | 対象ファイル全体と，そこから影響を受ける関連ファイル | 1コミットの差分(`git -C <対象リポジトリの作業ディレクトリの絶対パス> show <40桁のSHA>`で取得)．ファイル全体は差分だけでは処理内容が読み取れない場合の参考にとどめ，列挙対象にはしない | 初回は変更したファイルと，そこから影響を受ける関連ファイル．2回目以降は`gh pr diff <PR番号> --repo tt-and-tk/<repo> --name-only`で確認できるファイルに絞る(トークン消費を抑えるため) |
| 呼び出し方 | 「レビューに使うモデル」で同じモデルに決まる観点とだけ，まとめて1回で呼び出してよい | この列の観点同士に限り，まとめて1回で呼び出してよい(定型指示の扱いが他の観点と異なるため) | 「レビューに使うモデル」で同じモデルに決まる観点とだけ，まとめて1回で呼び出してよい |
| 定型指示 | すべて伝える | 「疑う視点」「軽微な指摘」「起票済み不具合」は伝えない(該当箇所を軽重によらず列挙させ，妥当性の判断も不具合の報告も求めないため)．「先入観を持たない」は伝えず，代わりに「差分だけでは処理内容が読み取れない場合は参考として対象ファイル全体や今回対応中のissueやPRの内容を読んでください．ただし，列挙対象は差分部分に限ってください」を伝える | すべて伝える |
| 過去の判断の申し送り | 該当しない(2回目以降の呼び出しがないため) | 行わない(レビュアーに過去の判断を伝える必要がないため) | 行う |

**回数上限に達した時点で残っている指摘は対応せず，理由をPRコメントに残してその観点の呼び出しを終了する．** ただし，issueのゴールを満たさなくなる指摘，および正しさが壊れる指摘については，上限に関わらず対応する．人間レビューへの対応後にこのループを再度実行する場合は，人間の判断を経ているため回数を数え直す．

**過去の判断の申し送りとは，2回目以降のレビュー依頼で，それまでに対応不要と判断した指摘および上限に達して打ち切った指摘とその理由をプロンプトに含めることをいう．** レビュアーは呼び出しごとに独立しており過去の経過を知らないため，これを行わないと同じ指摘が繰り返し挙がり，ループが収束しなくなる．伝えるのは指摘内容と対応しない理由に限る(issueの内容や修正方針の説明を書き足さない)．

#### レビューに使うモデル

`claude -p`には常に`--model`でモデルを指定する．指定しないと実行側と同じモデルがレビューすることになり，そのモデル自身の判断の癖・盲点を見抜けないためである．モデルは実行側の判断で選ばず，下表と衝突回避の規則で機械的に決める．指定には別名(`haiku`・`sonnet`・`opus`・`fable`)を使い，バージョン付きのIDは使わない(リリースのたびに書き換えが必要になるため)．

| 観点 | モデル | 理由 |
|:-|:-|:-|
| 全体レビュー・整合性レビュー・ハードウェア記述レビュー | `fable` | ファイルや仕様をまたぐ矛盾の発見，合成可否など，難しい判断を要するため |
| 新規読者理解可能性レビュー・コーディング規約レビュー | `haiku` | 推論力の高いモデルほど文脈から行間を埋めてしまい記述漏れや規約違反を見逃すため，あえて推論力を抑えたモデルに列挙させる |
| 上記以外の観点(実行側が追加した観点を含む) | `sonnet` | 通常の判断で足りるため |

**衝突回避: 表のモデルが実行側自身のモデルと同じ場合は，`haiku` < `sonnet` < `opus` < `fable`の順で1段上のモデルを使う．`fable`は上がないため`opus`を使う．** これにより，実行側が`sonnet`・`opus`・`fable`のいずれであっても，自分以外の3モデルがレビューに使われる．`haiku`の観点はこの規則の対象外とし，実行側によらず`haiku`を使う(妥当性の判断を求めない列挙であり，自己レビューの弊害が当たらないため)．

実行側のモデルは推測せず，システムプロンプト中で実行側自身のモデルを名指ししている1文に，上記の別名のどれが含まれるかで判定する(大文字・小文字は区別しない．モデル一覧や比較の文にも別名が現れるため，それらは判定に使わない)．セッション中にモデルが切り替わりうるため，`claude -p`を呼び出すたびにその時点の記述で判定する．記述がない場合や別名のどれも含まれない場合は，衝突なしとして表のモデルをそのまま使う．

#### レビュー依頼文言の作り方

**レビュー依頼文言には，今回のissueの内容・修正方針・修正時に気を付けた点・想定される問題箇所を書かない．** 実行側が意識して直した事柄をそのまま伝えると，既に確認済みの範囲を再確認させるだけになり，レビューが実行側の認識の内側に閉じてしまうためである．このルールは成果物を対象とする本項のレビューにのみ適用し，方針そのものを対象とする手順3の設計レビューには適用しない．依頼文言に書いてよいのは次の3つと，過去の判断の申し送りに限る．

1. レビュー対象(リポジトリ・ファイルパス・コミットのSHAなど．範囲は上表の「レビュー対象」に従う)
2. 観点名と，その観点の定義(観点一覧に記載された文面をそのまま用いる．実行側が独自に定義した観点の場合は，同程度の抽象度で書く)．複数観点をまとめて呼び出す場合は，指摘ごとにどの観点によるものかを明記するよう求める
3. 下記の定型指示のうち，上表の「定型指示」で伝えないとされていないもの

定型指示(観点によらず同じ文面で伝える指示)は次のとおりであり，レビュアーへはこの文面のまま伝える．`claude -p`にはツールの技術的制限(`--allowedTools`/`--disallowedTools`)を付与せず，すべてプロンプト文言で指示する．

- **修正しない**: レビューのみを行い，修正は行わないでください
- **先入観を持たない**: 今回対応中のissueやPRの内容は参照せず，成果物だけを見て判断してください
- **すべて報告する**: 気づいた点は，修正せずすべてレビュー結果として報告してください
- **疑う視点**: 妥当だと追認するのではなく，欠陥・考慮漏れを疑う視点で確認してください
- **軽微な指摘**: 誤解や手戻りにつながらない軽微な指摘は報告しないでください
- **起票済み不具合**: 気づいた不具合のうち，`gh issue list --repo tt-and-tk/<repo>`で確認できる起票済み(未クローズ)のものは報告不要です
- **指摘なしでよい**: 指摘すべき項目が一件もない場合は，無理に指摘を作らず指摘なしの旨を報告してください

作業ブランチ名にissue番号が含まれるため，レビュアーが辿ろうとすれば経緯に辿り着けてしまうが，ここでの目的は依頼文言による誘導をなくすことであり，技術的な遮断までは行わない．

呼び出しは次の形で行う．`--model`には「レビューに使うモデル」で決めたモデルを指定する．`--add-dir`は，別リポジトリ(別プロジェクト)のファイルを読ませる必要がある場合に，そのディレクトリへの読み取りアクセスを付与するために付ける(ワークスペースの信頼状態に関わらず有効)．**4.1で疑似隔離のcloneを作って作業している場合，そのリポジトリについて指定するのはclone先のディレクトリであり，元のローカルディレクトリではない．** 元を指すと今回の変更が反映されていないコピーをレビューさせることになり，何も指摘が出ないまま素通りする．

```
claude -p --model <モデル> [--add-dir <別リポジトリのパス>...] -- "<レビュー依頼文言>" > review-<観点を表す語句>.md
```

出力先のファイル名は観点ごとに変える(同一観点を再度呼び出したときの上書きは許容するが，異なる観点を並列に実行したときの書き込み衝突は避けるため)．観点間は独立しているため，必要なら並列に実行してよい．複数観点を1回の呼び出しにまとめる場合は，出力ファイル名は`review.md`のように単一でよい．

#### 指摘への対応と記録

観点ごとの呼び出しそれぞれについて，対応した指摘一つずつコミットを行う(対応しなかった指摘にはコミットは発生しない)．プッシュについてはまとめて行ってよいが，**対応した指摘のインラインコメントは，該当するコミットをpushした後に投稿する**(未pushのコミットを指すコメントは受け付けられない)．  
レビュー指摘への対応方針(AIレビュー・人間レビューの両方に共通する原則)と，対応内容を残すインラインコメントの書式・作成コマンドは，末尾の「レビュー指摘への向き合い方」を参照．  
レビュー結果の修正がまだ4.1〜4.3を行っていない他のリポジトリにも及ぶ場合，そのリポジトリが手順4冒頭の例外に当たれば，このセッションでそのリポジトリについても4.1〜4.4を行って対応する．例外に当たらなければ，手順4冒頭の原則どおり，そのリポジトリのプロジェクトで本スキルを実行するようユーザーに依頼する．  

観点ごとの呼び出し1回が終わるごとに，その回の指摘内容と各指摘への対応状況(対応した内容／対応しなかった理由)を要約したサマリーコメントをPRに投稿する．複数観点を1回の呼び出しにまとめた場合は，コメントに観点名を明記する．出力ファイルはこの後削除するため，このサマリーコメントをレビュー経過の恒久的な記録とする．

レビューで，起票済みでない既存不具合(今回のissueのゴールから外れるもの)が報告された場合，その場で`issue-create`スキルによる起票は行わない．指摘された既存不具合は，サマリーコメントに既存不具合と識別できる形で残した上で控えておき，手順6でユーザーに提示する．

自動レビューが投稿するコメント(このサマリーコメント，および後述のインラインコメント作成・返信)は，人間の投稿と区別できるよう，`GH_TOKEN`環境変数でbotアカウントのトークン(`~/.gh-bot-token`)を明示してその1コマンドの実行時だけ切り替える．コミット・push・PR作成には適用せず，従来どおりの既定認証(人間のアカウント)を使う．

```
GH_TOKEN=$(cat ~/.gh-bot-token) gh pr comment <PR番号> --repo tt-and-tk/<repo> --body "<観点名>のレビュー結果: 指摘内容の要約と，各指摘への対応状況(対応した内容／対応しなかった理由)"
```

```
git add <変更したファイル>
git commit -m "<コミットメッセージ>"
git push
```

疑似隔離のcloneで作業している場合は，4.1の規定に従い`git -C <絶対パス>`形式で実行する(以降も同じ)．

レビュー結果の出力ファイルは，サマリーコメントを投稿した時点で役目を終える一時ファイルであるため，その回の呼び出しの終了時に削除する(並列に実行した他観点の出力を消さないよう，グロブではなく実際に出力したファイル名を指定する)．

```
rm -f <その回の呼び出しで出力したファイル>
```

### 4.5 人間レビューへの対応

Draftの解除はユーザーが手動で行う (AIは行わない)．  

ユーザーがPRにレビューコメントを追加した場合は取得して確認し，指摘があれば修正してコミット・pushする．疑似隔離のcloneで作業している場合は，4.1の規定に従い`git -C <絶対パス>`形式で実行する．対応方針は「レビュー指摘への向き合い方」(末尾)を参照．  
インラインのレビューコメントとPR全体へのコメントは別に取得するため，以下は両方実行する．

```
gh api --paginate repos/tt-and-tk/<repo>/pulls/<PR番号>/comments
gh api --paginate repos/tt-and-tk/<repo>/issues/<PR番号>/comments
```
```
git add <変更したファイル>
git commit -m "<コミットメッセージ>"
git push
```

**指摘一つずつについて，該当コメントへの返信で対応内容を伝える(必須)．** 修正した場合はその内容，対応しない場合はその理由(「レビュー指摘への向き合い方」参照)を返信する．インラインのレビューコメントにはスレッド返信，PR全体へのコメントには通常のコメントで返信するため，以下は該当する側のみ実行する．

```
GH_TOKEN=$(cat ~/.gh-bot-token) gh api repos/tt-and-tk/<repo>/pulls/<PR番号>/comments/<コメントID>/replies -f body="<対応内容>"
```
```
GH_TOKEN=$(cat ~/.gh-bot-token) gh pr comment <PR番号> --repo tt-and-tk/<repo> --body "<対応内容>"
```

人間レビューへの対応が終わったら，**4.4の自動レビューループを再度実行する**(どの観点をどれだけ回すかは4.4の実施条件に従う)．

## 5. マージ

マージはユーザー自身が行う (共有状態を変更する操作のため，スキルは代行しない)．  

## 6. マージ後の後始末

マージ完了の報告を受けたら，issueがクローズされたことを確認する．

```
gh issue view <番号> --repo tt-and-tk/<repo>
```

**`EnterWorktree`で作業した場合**(4.1)，`ExitWorktree`(`remove`)で作業ディレクトリとブランチをまとめて削除する(元のディレクトリに自動的に戻るため，`git checkout`は不要)．Vivadoプロジェクトを含むリポジトリ(`qurge`)では，Git管理外の合成の中間生成物も一緒に消える(実機での確認はマージ前に済んでいるため支障はない)．その後，マージされた内容を元のローカルリポジトリに反映するため，以下を実行する．

```
git pull
```

**疑似隔離(4.1でclone)を使った場合**，cloneしたディレクトリを，疑似隔離で扱ったリポジトリごとに削除する(ローカルブランチもディレクトリごと削除される．そのリポジトリ本体のローカルクローンには一切触れないため，そちらのブランチ削除は不要)．

```
rm -rf <cloneしたディレクトリの絶対パス>
```

疑似隔離のcloneを削除しただけでは，マージされた内容はそのリポジトリ本体のローカルクローンに反映されない．疑似隔離で扱ったリポジトリごとに，そのリポジトリの既存のローカルディレクトリ(`pc/`配下のディレクトリ)に対して以下を実行し，最新化する．

```
git -C <既存のローカルディレクトリの絶対パス> pull
```

**セッションのリポジトリの`EnterWorktree`と疑似隔離を同一セッションで両方使った場合**，4.1の順序どおり`EnterWorktree`を先に実行していれば，疑似隔離のclone先はそのworktree配下にネストしている．この場合，`ExitWorktree`を先に実行するとworktreeごと疑似隔離のcloneも削除されるため，上記の`rm -rf`は不要になる(対象が既に存在せず空振りになる)．`ExitWorktree`を先に行う．

**修正対象のリポジトリに`for-pynthesis-skills`自身が含まれる場合**，上記に加えて以下を実行し，インストール済みプラグインを最新化する(反映にはClaude Codeの再起動が必要なため，実行後はユーザーに再起動が必要な旨を伝える)．**手順4冒頭の「セッションのリポジトリが修正対象に含まれない場合」に該当するケースでは，作業ディレクトリが`for-pynthesis-skills`のローカルリポジトリであっても，`for-pynthesis-skills`自身は修正対象ではなくこの条件には当てはまらない．**下記のプラグイン更新は行わない．

```
claude plugin marketplace update for-pynthesis-skills
claude plugin update for-pynthesis-skills@for-pynthesis-skills
```

4.4で控えた既存不具合は，同一ファイル・同一内容と判断できるものを除いた一覧を作り(複数リポジトリを扱った場合は，リポジトリをまたいで1つの一覧にまとめる)，後始末の完了報告にあわせてユーザーに提示する．起票するかどうかはユーザーが判断する．

# レビュー指摘への向き合い方

AIレビュー(`claude -p`)・人間レビューのいずれであっても，指摘を鵜呑みにしてそのまま従うのではなく，**本当に対応すべきか，このまま変更しない方が正しいのではないかを都度考えてから，対応する・しないを判断する．**

- 対応する必要がないと判断した指摘は，対応しなくてよい(指摘に反論する，あるいは意図的に対応しない場合も認められる)．次のいずれかに当てはまる指摘が典型例である
  - 想定される利用状況からかけ離れた，極端に限定的な条件でしか問題にならない指摘
  - 指摘自体は妥当だが，わざわざ手を入れるほどの重要度がない指摘
  - 前提が事実と異なる指摘(誤読・古い情報に基づくもの)．該当箇所を実際に確認した上で，誤りを指摘して反論する
  - 今回の変更が原因ではなく，今回のissueのゴールからも外れる指摘(既存の別問題や将来の拡張)．ただし4.4のレビュアーは今回の変更範囲を知らないため，今回変更したファイル・記述そのものに対する指摘を，issueに書かれていないことだけを理由に却下しない．このうち起票済みでない既存不具合については，4.4末尾の運用に従い，起票はせずユーザーへの報告対象として控えておく
  - ドキュメント・規定類の修正において，対応すると規定・手順が増え，得られる効果に対して運用の負担が見合わない指摘
- 対応した指摘は，PR上で指摘された箇所(ファイル・行)へのコメントとして対応内容を残し，あわせてコミットメッセージにも記録する．ここでのコメントはPR上のコメントであり，ソースコード中のコメント(`//`等)を書くことではない．どのコメントとして残すかはレビューの種類によって異なる
  - AIレビュー(`claude -p`)の指摘: 返信先のスレッドが存在しないため，指摘された箇所へのインラインコメントを新規に作成する．コメント単体ではどの観点で何を指摘されてどう直したかが分からないため，下記の書式に従って書く
  - 人間レビューの指摘: 4.5のスレッド返信がこれに当たる．元の記述と指摘は返信先のコメントから辿れるため，どう修正したかだけを返信する
- 対応しなかった指摘(無視・反論)は，指摘された箇所へのコメントではなく，PR自体へのコメント(4.4のサマリーコメント)にその理由を残す(黙って無視しない)．ただし人間レビューのインラインコメントに対しては，4.5のスレッド返信で理由を返信する(必須)．4.5の指摘単位の個別スレッド返信と，4.4の観点呼び出し単位のサマリーコメントは粒度が異なる別の仕組みであり，どちらも既存のルールに従う
- 対応する・しないの判断の考え方は，手順3(PR作成前の設計レビュー)の指摘にも適用する．記録先の規定のみPR作成後(手順4.4・4.5)の指摘に適用し，手順3で反論する場合は同項の運用(次のレビュー依頼プロンプトに含める)に従う

AIレビューの指摘に対するインラインコメントは，次の書式で書く．観点は，サマリーコメントと照らし合わせられるよう，レビュー依頼文言に書いた観点名をそのまま書く(複数観点をまとめた呼び出しでも指摘ごとに書く)．修正前は引用のため長さを問わず，指摘・対応はそれぞれ1〜2行に収める．

```markdown
- 観点: <指摘を出したレビューの観点名>
- 修正前: <指摘された記述・ソースを，要約せずそのまま引用する>
- 指摘: <レビュアーから何を指摘されたか>
- 対応: <どう修正したか>
```

指摘された箇所へのインラインコメントは以下で作成する．

```
GH_TOKEN=$(cat ~/.gh-bot-token) gh api repos/tt-and-tk/<repo>/pulls/<PR番号>/comments -f body="<上記の書式で書いた対応内容>" -f commit_id=<対応したコミットの40桁のSHA> -f path=<ファイルパス> -F line=<行番号> -f side=RIGHT
```

`commit_id`には，**そのPRのブランチにpush済みのコミットの，40桁の完全なSHA**を指定する．そのPRに含まれないコミットを指すと受け付けられないため，pushは必須である．SHAの桁数について公式に規定されているわけではないが，完全な形であれば確実に通るため，短縮形は使わない．指摘ごとにコミットを分けている以上，指摘の数だけ異なるSHAが必要になるため，各コミットの直後にそのSHAを控えておく．

```
git rev-parse HEAD
```

控え損ねた場合は，履歴から対象のコミットを特定して取得する．

```
git log --format="%H %s" origin/<デフォルトブランチ>..HEAD
```

疑似隔離のcloneで作業している場合，これらも4.1の規定どおり`git -C <絶対パス>`形式で実行する(現在のプロジェクトのSHAを取ってしまうと，PRに存在しないコミットを指すことになる)．

`path`と`line`は，そのPRの差分に含まれる行を指す必要がある．差分に無い箇所を指すコメントは作成できないため，指摘された箇所と実際に修正した箇所が離れている場合は，修正した側の行を指定する．

# 注意

- 人間の確認が必須なのは，手順3(修正方針の承認)と，破壊的操作(force push，reset --hard等)と，実機での動作確認(4.2．行う場合のみ)のみ．それ以外(ブランチ作成・実装・コミット・push・PR作成・レビューループ・レビューコメント対応)は連続して自動実行する
- 1issueに対して複数のPRがある場合，closeキーワードを持つPRは1つだけにする
- 影響リポジトリが不明な場合は，ユーザーに確認する
- マージは決して行わない
