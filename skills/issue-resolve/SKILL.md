# 概要

GitHub issueへの対応 (調査・ブランチ作成・修正・PR作成) を行う．粒度は1issue=1回の実行．対応が複数リポジトリにまたがる場合の進め方は手順4冒頭を参照．

# コマンド実行の規定

この規定は，スキル本文に記載されたコマンドの実行と，手順を進める中で実行側が自分で組み立てるコマンドの両方に適用する．

- スキル本文に記載されたコマンドは，記載されたままの形で実行する．オプションの追加・削除，引数の順序変更，コマンドに渡す文言をいったんシェル変数に格納してから参照する形への書き換え，末尾に`&& echo ...`をつないで成否を確認する形への書き換えなど，記載と異なる形にしない．成否確認や可読性のための書き換えも同様に行わない．実行許可の判定はコマンド全体に対して行われるため，わずかな書き換えでも許可設定と一致せず，不要な確認プロンプトで作業が中断される
- 1回のBash呼び出しで実行するコマンドは1つとし，`&&`・`;`・`|`で複数のコマンドをつながない(スキル本文にその形で記載されている場合を除く)．1つのコードブロックに複数行のコマンドが並んでいる場合も，まとめて1回で実行せず，行ごとに1回のBash呼び出しに分ける．どの行を実行するかは本文の説明に従い，択一の選択肢として複数のコマンドが並んでいる場合は該当するものだけを実行する．1行実行するごとに結果を確認し，失敗していれば以降の行を実行せず原因を解消する．実行側が自分で組み立てるコマンドで出力を絞り込みたい場合は，パイプでつなぐのではなく`Grep`・`Read`ツールを使うか，コマンド自身のオプションで絞る(本文に記載されたコマンドは，出力が大きくてもオプションを足さずそのまま実行する)．`> <ファイル>`によるファイル出力は，本文が示す用法に従う限り，本文に記載のないコマンドでも用いてよい
- `cd`については上記の例外を認めず，常に単独のBash呼び出しにする．`cd <パス> && <コマンド>`のような複合コマンドにはせず，`cd <パス>`単独の呼び出しと，その後の素のコマンド呼び出しに分ける．作業ディレクトリはworktree内にとどまる限りツール呼び出しをまたいで保持されるが，worktreeの外にあるディレクトリへは`cd`しても次のBash呼び出しには維持されない
- 次のものは改変に当たらない
  - `<番号>`のようなプレースホルダを実際の値に置き換えること
  - `[...]`で任意と示されたオプションを付ける，または付けないこと
  - 「〜を依頼する文言」のように，スキル本文が渡すべき内容を説明しているだけの箇所を，実際の文言に書き起こすこと(ただし文言はコマンドラインに直接書き，シェル変数への格納や別ファイルへの書き出しを経由しない．改行を含む長い本文は，ヒアドキュメントでコマンドライン中に直接書いてよい)
  - スキル本文の説明が指示している変形(`git -C <絶対パス>`形式への変換，`--head`の明示，`--add-dir`に指定するディレクトリの読み替えなど)
- 記載どおりのコマンドでは目的を達成できない場合は，黙って改変せず，記載どおりでは達成できない理由と実際に実行するコマンドをユーザーに説明した上で，回避となるコマンドを実行する(ユーザーの応答は待たずに作業を進めてよい)．人間が介在しない非対話的な実行の場合は，同じ説明を出力に含める

# 手順

## 1. issue内容の確認

```
gh issue view <番号> --repo <owner>/<repo>
```

## 2. 調査

原因調査を行い，影響範囲 (対象リポジトリ・対象ファイル) を特定する．issue本文中に推測が書かれている場合は，事実かどうかをここで検証する．

## 3. 修正方針の承認

調査結果と修正方針を固めたら，ユーザーに提示する前に`claude -p`による設計レビューを行う．対象は方針テキストだけでなく，関連する既存仕様・ソース(矛盾がないか判断するのに必要な範囲)も含める．技術的なツール制限は付与せず，プロンプト文言で「読み取りのみを行い，修正は行わないこと」を指示する．関連ファイルが別リポジトリ(別プロジェクト)にある場合は，`--add-dir <ディレクトリ>`でそのディレクトリへの読み取りアクセスを明示的に付与する(この時点では4.1のcloneをまだ作っていないため，各リポジトリの既存のローカルディレクトリを指定する)．

```
claude -p [--add-dir <別リポジトリのパス>...] -- "issue #<番号>(<owner>/<repo>)への対応方針(設計)のレビューを依頼する文言．方針の内容と，判断に必要な関連ファイル<パス>を提示し，既存仕様との矛盾・考慮漏れがないか確認してもらう．必要なら`gh issue view`でissue詳細を取得してよいことを伝える．読み取りのみ行い，修正は行わないことを明記する"
```

レビュー指摘のうち対応すべきと判断したものは，ユーザーに提示する前に方針へ反映する(対応方針は末尾「レビュー指摘への向き合い方」を参照)．反論する場合，設計段階ではまだコミットが存在しないため記録先を設けず，同じ指摘が再度出た場合に「以前この理由で対応しなかった」旨を次のレビュー依頼時のプロンプトに含めればよい．

その上で，調査結果と(設計レビューを反映済みの)修正方針をユーザーに提示し，承認を得る．**これが実装前の最後の確認ポイント**であり，承認後は手順4を人間の追加確認なしに連続して実行する．  
ここでは，特に聞かれない限り具体的なソース内容を提示する必要はない．ソースのうち，どの仕事をする部分をどのように修正するかを提示できれば十分．  

## 4. リポジトリごとの実装〜PR作成

影響リポジトリごとに以下を行う．**複数リポジトリに影響する場合，1つのセッションで複数リポジトリを串刺しに編集しない．**このリポジトリでの対応が完了したら，他の影響リポジトリについては，対象リポジトリと該当issue番号を明示した上で，そのリポジトリのプロジェクトで本スキルを実行するようユーザーに依頼する(このセッションから直接他リポジトリを操作しない)．issue自体は1つのままでよく，実装の実行単位だけをリポジトリごとに分ける．

**例外(`specification`):** `specification`リポジトリはClaude Codeプロジェクトを持たない(非プロジェクトという既存設計のため)ため，串刺し禁止ルールの対象外とする．影響リポジトリに`specification`が含まれる場合，`specification`に対しては現在のセッションから直接ブランチ作成・ファイル操作・PR作成を行ってよい(別セッションへの依頼は不要)．`specification`以外の複数リポジトリにまたがる場合は，それらの間では引き続き串刺し禁止ルールが適用される．

### 4.1 作業場所の準備

`EnterWorktree`(name: `fix/issue-<番号>-<内容を表す短い語句>`)で専用の作業ディレクトリとブランチを作成してから作業する．`EnterWorktree`はブランチ作成まで一体で行うため，**この場合は，次のVivadoプロジェクト向けに示す`git checkout -b`を含むコードブロックを実行しない**．

**`EnterWorktree`が実際に作るブランチ名は，渡した`name`とは一致しない．** 接頭辞の付与やスラッシュの置換が行われるため，以降の手順でブランチ名を書く場合は，渡した`name`をそのまま使わず，作成直後に実際の名前を確認して用いる．

```
git branch --show-current
```

**ただしVivadoプロジェクトを含むリポジトリの場合は対象外とする．** XPRファイルの絶対パス依存やキャッシュ生成コストがあるため，worktreeでの作業は行わず，従来通り単一ディレクトリで直列に作業する(以下のコードブロックでローカルを最新化し，作業用ブランチを作成する)．

```
git checkout <デフォルトブランチ>
git pull
git checkout -b fix/issue-<番号>-<内容を表す短い語句>
```

**`specification`の場合は`EnterWorktree`も使えない．** `EnterWorktree`は現在のリポジトリまたはそこにネストしたリポジトリにしか使えず，`specification`は現在のリポジトリと兄弟関係にあるためである．代わりに，`specification`をリモートから直接cloneして疑似的な隔離を作る(以降これを**疑似隔離**と呼ぶ)．**GitHub上のリモートから取得した独立した作業用コピーであり，`specification`のローカルディレクトリや，現在作業しているプロジェクトのworktreeとは無関係である．** clone先は，サンドボックスの書き込み制限により`specification`と兄弟の場所には作れないため，現在のプロジェクト自身のディレクトリツリー内(`<現在のプロジェクトルート>/.worktrees/`配下)とする．

**`<現在のプロジェクトルート>`は，このセッションが起動した元のプロジェクトディレクトリを指す．`EnterWorktree`のworktree(`.claude/worktrees/<name>/`配下)には作らない．**

```
gh repo clone tt-and-tk/specification "<現在のプロジェクトルート>/.worktrees/specification-fix-issue-<番号>-<内容を表す短い語句>"
git -C "<現在のプロジェクトルート>/.worktrees/specification-fix-issue-<番号>-<内容を表す短い語句>" checkout -b fix/issue-<番号>-<内容を表す短い語句>
```

各プロジェクトの`.gitignore`は`.worktrees/`を除外済みである前提とする(未対応の場合は別issueで一括対応する)．

**この方法で作業する場合に限り，以降の手順で`specification`に対して実行するgitコマンドは，すべて`git -C <cloneしたディレクトリの絶対パス> ...`の形式で実行する．** `add`・`commit`・`push`だけでなく，`diff`・`status`・`log`・`rev-parse`など読み取り系も含めた全てが対象である．cloneしただけではセッションの作業ディレクトリは切り替わらず，clone先はセッションの作業ディレクトリの外にあるため`cd`しても次のBash呼び出しには維持されない．形式を省くと現在のプロジェクトを操作してしまう．`EnterWorktree`を使う場合とVivadoプロジェクトの場合は，セッションの作業ディレクトリが対象リポジトリ内にあるため素の形式でよい．

### 4.2 修正

手順3で承認された方針に基づいて修正を行う．

疑似隔離で作業している場合，**編集するのはclone先のファイルであり，元のローカルディレクトリのファイルではない．** 手順3の設計レビューでは元のローカルディレクトリを読み取り対象にしているため，そのパスのまま編集に入ると取り違える．元を編集すると，clone先には変更が無いまま空のコミット・PRになり，かつローカルの`specification`に意図しない変更が残る．

### 4.3 コミット・push・PR作成

```
git add <変更したファイル>
git commit -m "<コミットメッセージ>"
git push -u origin HEAD
gh pr create --repo <owner>/<repo> --title "<タイトル>" --body "<本文>" [--draft]
```

push先は，ブランチ名を書かず`HEAD`で現在のブランチを指す(`EnterWorktree`が作るブランチ名は`name`と一致しないため，名前を書くと存在しない別のブランチを新規に作ってしまう)．

PR作成時の`--body`に，closeキーワード (`Closes owner/repo#番号`) またはリンクのみ (`Related to owner/repo#番号`) を含める．closeキーワードは1issueにつき1箇所のPRのみに付与する (issueが存在するリポジトリのPR，またはユーザーが指定したPR)．それ以外のリポジトリのPRは`Related to owner/repo#番号`のみを記載する．  

**`--draft`は，closeキーワードを持つPRにのみ付ける．** マージするとissueが閉じるPRであることを一目で分かるようにするための運用．closeキーワードを持たない(`Related to`のみの)PRはissueを閉じないため，通常のPR(Ready)として作成する．  

**`specification`の疑似隔離(4.1でcloneしたディレクトリ)で作業している場合**，上記のgitコマンドは4.1の規定に従って`git -C <cloneしたディレクトリの絶対パス> ...`の形式で実行する．あわせて`gh pr create`には`--head fix/issue-<番号>-<内容を表す短い語句>`を明示してpush先ブランチを指定する(`gh`はセッションのカレントディレクトリからブランチを判定するため，明示しないと別のブランチを指す)．

### 4.4 自動レビューループ

`claude -p`によるレビューを行い，修正すべきと判断した指摘がなくなるまで，人間の確認なしに修正・再レビューを繰り返す．変更内容のうち説明が必要な箇所は，PRへのコメントまたはコミットメッセージで補足する．  

**繰り返しには回数の上限を設ける．** 観点ごとの呼び出し回数は，修正量に応じて2〜5回程度までとする．上限に達した時点で残っている指摘は対応せず，理由をPRコメントに残してその観点の呼び出しを終了する．ただし，issueのゴールを満たさなくなる指摘，および正しさが壊れる指摘については，上限に関わらず対応する．人間レビューへの対応後にこのループを再度実行する場合は，人間の判断を経ているため回数を数え直す．  

レビューは観点ごとに`claude -p`の呼び出しを分ける．各呼び出しの出力は`review-<観点を表す語句>.md`のように観点ごとに異なるファイル名へ出力し，観点間は独立して(必要なら並列に)実行してよい．複数観点を1回の呼び出しにまとめる場合は，出力ファイル名は`review.md`のように単一でよい．代表的な観点は以下の通り(修正内容に応じて他の観点を追加してもよい)．

- **全体レビュー**: 対象ファイル全体を読み，記述の矛盾・抜け漏れ・不具合の有無を確認する．**最低限これだけは毎回実施する**
- **テストコードの網羅性レビュー**: 仕様書やソースの内容を踏まえ，追加・変更した機能について，正常系・異常系を含め想定されるさまざまな使われ方に対してテストコードに考慮漏れがないかを確認する．機能の追加・変更を伴う修正の場合に行う
- **整合性レビュー**: `specification`等の既存ドキュメント，同一リポジトリ内の他ファイル，他リポジトリの関連ファイル，あるいは同一ファイル内の過去の記述との間に，矛盾や対応漏れがないかを確認する．既存ドキュメント・関連ファイルに影響する変更を行った場合や，仕様変更・新機能の追加によって過去の制限が撤廃された場合など，関連箇所の更新漏れが起きやすい状況で行う
- **可読性・保守性レビュー**: 命名・重複・複雑度など，読みやすさ・保守しやすさの観点から確認する．ソースの追加・変更量が多い場合に行う
- **パフォーマンスレビュー**: 不要な処理・非効率な実装がないかを確認する．パフォーマンスに影響しうる変更の場合に行う

**全体レビュー以外の観点は，毎回実施する必要はない．** 修正の複雑性・影響範囲に応じて，どの観点で何回`claude -p`を呼ぶかは実行側(このスキルを実行しているセッション)の判断に委ねる．軽微な修正では観点をまとめて1回の呼び出しにしてよく，影響範囲が広い・設計判断を伴う修正では観点ごとに呼び出しを分けることを推奨する．

レビュー観点は上記の例に限られない．修正内容に応じて実行側が必要と判断した独自の観点を定義し，`claude -p`へのレビュー依頼に反映してよい．

レビューに別リポジトリ(別プロジェクト)のファイルを読む必要がある場合は，`--add-dir <ディレクトリ>`でそのディレクトリへの読み取りアクセスを明示的に付与する(ワークスペースの信頼状態に関わらず有効)．**4.1で疑似隔離のcloneを作って作業している場合，そのリポジトリについて指定するのはclone先のディレクトリであり，元のローカルディレクトリではない．** 元を指すと今回の変更が反映されていないコピーをレビューさせることになり，何も指摘が出ないまま素通りする．

#### レビュー依頼文言の作り方

**レビュー依頼文言には，今回のissueの内容・修正方針・修正時に気を付けた点・想定される問題箇所を書かない．** 実行側が意識して直した事柄をそのまま伝えると，既に確認済みの範囲を再確認させるだけになり，レビューが実行側の認識の内側に閉じてしまうためである．このルールは成果物を対象とする本項のレビューにのみ適用し，方針そのものを対象とする手順3の設計レビューには適用しない．依頼文言に書いてよいのは次の3つに限る．

- 観点名と，その観点の定義(上記の一覧に記載されたもの．実行側が独自に定義した観点の場合は，同程度の抽象度で書く)
- レビュー対象(リポジトリ・ファイルパス)．変更したファイルだけを挙げると，レビューの及ぶ範囲が結局は実行側の認識の内側に収まってしまうため，そこから影響を受ける関連ファイルも対象に含めてよい
- 下記の共通指示

共通指示として毎回伝える内容は以下の通り．`claude -p`にはツールの技術的制限(`--allowedTools`/`--disallowedTools`)を付与せず，すべてプロンプト文言で指示する．

- レビューのみを行い，修正は行わないこと
- issueやPRの内容は参照せず，成果物だけを見て判断すること
- 気づいた点は，修正はせずすべてレビュー結果として報告すること
- 妥当だと追認するのではなく，欠陥・考慮漏れを積極的に疑う視点で確認すること

作業ブランチ名にissue番号が含まれるため，レビュアーが辿ろうとすれば経緯に辿り着けてしまうが，ここでの目的は依頼文言による誘導をなくすことであり，技術的な遮断までは行わない．

レビュアーは呼び出しごとに独立しており過去の経過を知らないため，2回目以降のレビュー依頼では，それまでに対応不要と判断した指摘，および上限に達して打ち切った指摘とその理由をプロンプトに含める(同じ指摘が繰り返し挙がり，ループが収束しなくなるのを防ぐ)．これは上記の「書かない」の唯一の例外であり，伝えるのは指摘内容と対応しない理由に限る(issueの内容や修正方針の説明を書き足さない)．

観点ごとの呼び出しそれぞれについて，対応した指摘一つずつコミットを行う(対応しなかった指摘にはコミットは発生しない)．プッシュについてはまとめて行ってよいが，**対応した指摘のインラインコメントは，該当するコミットをpushした後に投稿する**(未pushのコミットを指すコメントは受け付けられない)．  
レビュー指摘への対応方針は，末尾の「レビュー指摘への向き合い方」を参照(AIレビュー・人間レビューの両方に共通する原則)．  
レビュー結果の修正が他のプロジェクトにも及ぶ場合は，同じissueに対応する設定のブランチを切ってから対応する．  

観点ごとの呼び出し1回が終わるごとに，その回の指摘内容と各指摘への対応状況(対応した内容／対応しなかった理由)を要約したサマリーコメントをPRに投稿する．複数観点を1回の呼び出しにまとめた場合は，コメントに観点名を明記する．`review-<観点>.md`は同一観点を再度呼び出すと上書きされ経過を追えなくなるため，このサマリーコメントをレビュー経過の恒久的な記録とする．

```
gh pr comment <PR番号> --repo <owner>/<repo> --body "<観点名>のレビュー結果: 指摘内容の要約と，各指摘への対応状況(対応した内容／対応しなかった理由)"
```

全体レビューの例:

```
claude -p [--add-dir <別リポジトリのパス>...] -- "<対象ファイルのパス>のレビューを依頼する文言．ファイル全体を読み，記述の矛盾・抜け漏れ・不具合の有無を確認してほしい．レビューのみを行い修正はしないこと，issueやPRの内容は参照せず成果物だけを見て判断すること，気づいた点は修正せずすべて報告すること，妥当だと追認するのではなく欠陥・考慮漏れを積極的に疑う視点で確認することを明記する" > review-whole.md
```

```
git add <変更したファイル>
git commit -m "<コミットメッセージ>"
git push
```

疑似隔離のcloneで作業している場合は，4.1の規定に従い`git -C <絶対パス>`形式で実行する(以降も同じ)．

### 4.5 人間レビューへの対応

Draftの解除はユーザーが手動で行う (AIは行わない)．  

ユーザーがPRにレビューコメントを追加した場合は取得して確認し，指摘があれば修正してコミット・pushする．疑似隔離のcloneで作業している場合は，4.1の規定に従い`git -C <絶対パス>`形式で実行する．対応方針は「レビュー指摘への向き合い方」(末尾)を参照．

```
gh api repos/<owner>/<repo>/pulls/<PR番号>/comments
gh api repos/<owner>/<repo>/issues/<PR番号>/comments
```
```
git add <変更したファイル>
git commit -m "<コミットメッセージ>"
git push
```

**指摘一つずつについて，該当コメントへの返信で対応内容を伝える(必須)．** 修正した場合はその内容，対応しない場合はその理由(「レビュー指摘への向き合い方」参照)を返信する．インラインのレビューコメントにはスレッド返信，PR全体へのコメントには通常のコメントで返信する．

```
gh api repos/<owner>/<repo>/pulls/<PR番号>/comments/<コメントID>/replies -f body="<対応内容>"
```
```
gh pr comment <PR番号> --repo <owner>/<repo> --body "<対応内容>"
```

人間レビューへの対応が終わったら，**4.4の自動レビューループを再度実行する**(全体レビューは引き続き必須．それ以外の観点をどれだけ回すかは，修正内容に応じて実行側の判断に委ねる)．

マージはユーザー自身が行う (共有状態を変更する操作のため，スキルは代行しない)．

# レビュー指摘への向き合い方

AIレビュー(`claude -p`)・人間レビューのいずれであっても，指摘を鵜呑みにしてそのまま従うのではなく，**本当に対応すべきか，このまま変更しない方が正しいのではないかを都度考えてから，対応する・しないを判断する．**

- 対応する必要がないと判断した指摘は，対応しなくてよい(指摘に反論する，あるいは意図的に対応しない場合も認められる)．次のいずれかに当てはまる指摘が典型例である
  - 想定される利用状況からかけ離れた，極端に限定的な条件でしか問題にならない指摘
  - 指摘自体は妥当だが，わざわざ手を入れるほどの重要度がない指摘
  - 前提が事実と異なる指摘(誤読・古い情報に基づくもの)．該当箇所を実際に確認した上で，誤りを指摘して反論する
  - 今回の変更が原因ではなく，今回のissueのゴールからも外れる指摘(既存の別問題や将来の拡張)．ただし4.4のレビュアーは今回の変更範囲を知らないため，今回変更したファイル・記述そのものに対する指摘を，issueに書かれていないことだけを理由に却下しない
  - ドキュメント・規定類の修正において，対応すると規定・手順が増え，得られる効果に対して運用の負担が見合わない指摘
- 対応した指摘は，PR上で指摘された箇所(ファイル・行)へのコメントとして対応内容を残し，あわせてコミットメッセージにも記録する．ここでのコメントはPR上のコメントであり，ソースコード中のコメント(`//`等)を書くことではない．人間レビューの指摘は4.5のスレッド返信がこれに当たる．AIレビュー(`claude -p`)の指摘には返信先のスレッドが存在しないため，指摘された箇所へのインラインコメントを新規に作成する
- 対応しなかった指摘(無視・反論)は，指摘された箇所へのコメントではなく，PR自体へのコメント(4.4のサマリーコメント)にその理由を残す(黙って無視しない)．ただし人間レビューのインラインコメントに対しては，4.5のスレッド返信で理由を返信する(必須)．4.5の指摘単位の個別スレッド返信と，4.4の観点呼び出し単位のサマリーコメントは粒度が異なる別の仕組みであり，どちらも既存のルールに従う
- 対応する・しないの判断の考え方は，手順3(PR作成前の設計レビュー)の指摘にも適用する．記録先の規定のみPR作成後(手順4.4・4.5)の指摘に適用し，手順3で反論する場合は同項の運用(次のレビュー依頼プロンプトに含める)に従う

指摘された箇所へのインラインコメントは以下で作成する．

```
gh api repos/<owner>/<repo>/pulls/<PR番号>/comments -f body="<対応内容>" -f commit_id=<対応したコミットの40桁のSHA> -f path=<ファイルパス> -F line=<行番号> -f side=RIGHT
```

`commit_id`には，**そのPRのブランチにpush済みのコミットの，40桁の完全なSHA**を指定する．そのPRに含まれないコミットを指すと受け付けられないため，pushは必須である．SHAの桁数について公式に規定されているわけではないが，完全な形であれば確実に通るため，短縮形は使わない．指摘ごとにコミットを分けている以上，指摘の数だけ異なるSHAが必要になるため，各コミットの直後にそのSHAを控えておく．

```
git rev-parse HEAD
```

控え損ねた場合は，履歴から対象のコミットを特定して取得する．

```
git log --format="%H %s" origin/<デフォルトブランチ>..HEAD
```

疑似隔離のcloneで作業している場合，これらも4.1の規定どおり`git -C <絶対パス>`形式で実行する(現在のプロジェクトのSHAを取ってしまうと，PRに存在しないコミットを指すことになる)．

`path`と`line`は，そのPRの差分に含まれる行を指す必要がある．差分に無い箇所を指すコメントは作成できないため，指摘された箇所と実際に修正した箇所が離れている場合は，修正した側の行を指定する．

# 注意

- 人間の確認が必須なのは，手順3(修正方針の承認)と，破壊的操作(force push，reset --hard等)のみ．それ以外(ブランチ作成・実装・コミット・push・PR作成・レビューループ・レビューコメント対応)は連続して自動実行する
- 1issueに対して複数のPRがある場合，closeキーワードを持つPRは1つだけにする
- 影響リポジトリが不明な場合は，ユーザーに確認する
- マージは決して行わない
- コマンドの実行形式は冒頭の「コマンド実行の規定」に従う
