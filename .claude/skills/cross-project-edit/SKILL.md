# コマンド実行の規定

この規定は，スキル本文に記載されたコマンドの実行と，手順を進める中で実行側が自分で組み立てるコマンドの両方に適用する．

- スキル本文に記載されたコマンドは，記載されたままの形で実行する．オプションの追加・削除，引数の順序変更，コマンドに渡す文言をいったんシェル変数に格納してから参照する形への書き換え，末尾に`&& echo ...`をつないで成否を確認する形への書き換えなど，記載と異なる形にしない．成否確認や可読性のための書き換えも同様に行わない．実行許可の判定はコマンド全体に対して行われるため，わずかな書き換えでも許可設定と一致せず，不要な確認プロンプトで作業が中断される
- 1回のBash呼び出しで実行するコマンドは1つとし，`&&`・`;`・`|`で複数のコマンドをつながない(スキル本文にその形で記載されている場合を除く)．1つのコードブロックに複数行のコマンドが並んでいる場合も，まとめて1回で実行せず，行ごとに1回のBash呼び出しに分ける．どの行を実行するかは本文の説明に従い，択一の選択肢として複数のコマンドが並んでいる場合は該当するものだけを実行する．1行実行するごとに結果を確認し，失敗していれば以降の行を実行せず原因を解消する(互いに独立したコマンドを本文の指示に従って並列に実行する場合を除く)．実行側が自分で組み立てるコマンドで出力を絞り込みたい場合は，パイプでつなぐのではなく`Grep`・`Read`ツールを使うか，コマンド自身のオプションで絞る(本文に記載されたコマンドは，出力が大きくてもオプションを足さずそのまま実行する)．`> <ファイル>`によるファイル出力は，本文が`>`を用いている用法(レビュー結果をファイルに出力する場合)と同じ目的であれば，本文に記載のないコマンドでも用いてよい
- `cd`については上記の例外を認めず，常に単独のBash呼び出しにする．`cd <パス> && <コマンド>`のような複合コマンドにはせず，`cd <パス>`単独の呼び出しと，その後の素のコマンド呼び出しに分ける．作業ディレクトリはworktree内にとどまる限りツール呼び出しをまたいで保持されるが，worktreeの外にあるディレクトリへは`cd`しても次のBash呼び出しには維持されない
- 次のものは改変に当たらず，上記の各項目より優先する
  - `<番号>`のようなプレースホルダを実際の値に置き換えること
  - `[...]`で囲まれたオプションを，本文が示す条件に従って付ける，または付けないこと(自由に選べるという意味ではない)
  - 「〜を依頼する文言」のように，スキル本文が渡すべき内容を説明しているだけの箇所を，実際の文言に書き起こすこと
  - コミットメッセージ・issue本文・PRの本文やコメント・`claude -p`に渡すレビュー依頼文言など，改行を含む文字列を引数として渡す際に，本文の`-m "<コミットメッセージ>"`のような単純なクォートを`-m "$(cat <<'EOF' … EOF)"`に組み替えること(オプションの書式が`-f body=`や`-- "<文言>"`であっても同様．ヒアドキュメントとコマンド置換でコマンドライン中に直接書く形であり，複数コマンドの連結にも当たらない．いったんシェル変数に格納したり，別ファイルに書き出して読み込ませたりはしない)
  - スキル本文の説明が指示している変形(`git -C <絶対パス>`形式への変換，`--head`の明示，`--add-dir`に指定するディレクトリの読み替えなど)
- 記載どおりのコマンドでは目的を達成できない場合は，黙って改変せず，記載どおりでは達成できない理由と実際に実行するコマンドをユーザーに説明した上で，回避となるコマンドを実行する(ユーザーの応答は待たずに作業を進めてよい．ただし回避となるコマンドが破壊的操作やGitHub上に公開される操作に当たる場合は，本文の規定に従って実行前に承認を得る)．出力が大きすぎて作業を続けられない場合も，同じ扱いとする．人間が介在しない非対話的な実行の場合は，同じ説明を出力に含める

# 手順

## 1. issue内容の確認

```
gh issue view <番号> --repo tt-and-tk/for-pynthesis-skills
```

## 2. 調査

原因調査を行い，影響リポジトリ(`specification`/`pynesis`/`pyntaxis`/`qurge`/`for-pynthesis-skills`自身のうち複数)と対象ファイルを特定する．

## 3. 修正方針の承認

調査結果と修正方針を固めたら，ユーザーに提示する前に`claude -p`による設計レビューを行う．対象は方針テキストだけでなく，関連する既存仕様・ソース(矛盾がないか判断するのに必要な範囲)も含める．技術的なツール制限は付与せず，プロンプト文言で「読み取りのみを行い，修正は行わないこと」を指示する．対象リポジトリが複数ある場合は，`--add-dir <ディレクトリ>`でそれぞれへの読み取りアクセスを明示的に付与する(この時点では4-1のcloneをまだ作っていないため，各リポジトリの既存のローカルディレクトリを指定する)．

```
claude -p [--add-dir <対象リポジトリのパス>...] -- "issue #<番号>(tt-and-tk/for-pynthesis-skills)への対応方針(設計)のレビューを依頼する文言．方針の内容と，判断に必要な関連ファイル<パス>を提示し，既存仕様との矛盾・考慮漏れがないか確認してもらう．必要なら`gh issue view`でissue詳細を取得してよいことを伝える．読み取りのみ行い，修正は行わないことを明記する"
```

レビュー指摘のうち対応すべきと判断したものは，ユーザーに提示する前に方針へ反映する(対応方針は末尾「レビュー指摘への向き合い方」を参照)．反論する場合，設計段階ではまだコミットが存在しないため記録先を設けず，同じ指摘が再度出た場合に「以前この理由で対応しなかった」旨を次のレビュー依頼時のプロンプトに含めればよい．

その上で，調査結果と(設計レビューを反映済みの)修正方針をユーザーに提示し，承認を得る．**これが実装前の最後の確認ポイント**であり，承認後は手順4を人間の追加確認なしに連続して実行する．

## 4. リポジトリごとの実装〜PR作成

影響リポジトリ全てについて，このセッション内で連続して以下を行う．

### 4-1. 作業場所の準備

**対象リポジトリに`for-pynthesis-skills`自身が含まれる場合，このセッションでは必ず`for-pynthesis-skills`のこの4-1(作業場所の準備)を他リポジトリのcloneより先に行う．** (4-2以降は，通常どおり影響リポジトリごとに連続して進めてよい．)他リポジトリのclone先(下記)は，このセッションの現在の作業ディレクトリを基準にするため，順序を誤ると先にcloneした他リポジトリの作業ディレクトリが，後から実行する`for-pynthesis-skills`自身の`EnterWorktree`による隔離範囲の外側になり，以降のgit操作がブロックされる．

`for-pynthesis-skills`自身の場合，`EnterWorktree`(name: `fix/issue-<番号>-<内容を表す短い語句>`)で専用の作業ディレクトリとブランチを作成する．**`EnterWorktree`が作るブランチ名は，渡した`name`に`worktree-`を接頭辞として付与し，`/`を`+`に置換した`worktree-fix+issue-<番号>-<内容を表す短い語句>`になる．** 以降の手順でブランチ名を書く場合は，この形式をそのまま用いる．

それ以外のリポジトリの場合，`EnterWorktree`は使わずリモートから直接cloneして隔離を作る．`EnterWorktree`は現在のリポジトリまたはそこにネストしたリポジトリにしか使えず，`for-pynthesis-skills`以外のリポジトリは現在のリポジトリと兄弟関係にあるため使えない．また，サンドボックスの書き込み制限により兄弟の場所には直接cloneを作れないため，clone先は，`pwd`で確認した作業中のローカルリポジトリ内(`<作業中のローカルリポジトリ>/.worktrees/`配下)とする．

**clone先の基準に`pwd`の実行結果を使う理由:** 他リポジトリのcloneを，`for-pynthesis-skills`自身の`EnterWorktree`のworktree内に作りたいためである．上記のとおり`for-pynthesis-skills`自身を先に処理していれば，`pwd`は自動的にそのworktree配下を指すため，他リポジトリのcloneも自動的にworktree内にネストする．

```
pwd
gh repo clone tt-and-tk/<リポジトリ名> "<作業中のローカルリポジトリ>/.worktrees/<リポジトリ名>-fix-issue-<番号>-<内容を表す短い語句>"
git -C "<作業中のローカルリポジトリ>/.worktrees/<リポジトリ名>-fix-issue-<番号>-<内容を表す短い語句>" checkout -b fix/issue-<番号>-<内容を表す短い語句>
```

各プロジェクトの`.gitignore`は`.worktrees/`を除外済みである前提とする(未対応の場合は別issueで一括対応する)．`EnterWorktree`のworktree配下にネストする場合も，そのworktreeは対象リポジトリと同じ内容をチェックアウトしているため，同じ`.gitignore`が有効である．

**cloneで作業するリポジトリに対して以降の手順で実行するgitコマンドは，すべて`git -C <cloneしたディレクトリの絶対パス> ...`の形式で実行する．** `add`・`commit`・`push`だけでなく，`diff`・`status`・`log`・`rev-parse`など読み取り系も含めた全てが対象である．cloneしただけではセッションの作業ディレクトリは切り替わらず，clone先はセッションの作業ディレクトリの外にあるため`cd`しても次のBash呼び出しには維持されない．形式を省くと別のリポジトリを操作してしまう．`EnterWorktree`を使う`for-pynthesis-skills`自身については，セッションの作業ディレクトリがその中にあるため素の形式でよい．

### 4-2. 修正

手順3で承認された方針に基づいて修正する．

cloneで作業しているリポジトリについては，**編集するのはclone先のファイルであり，元のローカルディレクトリのファイルではない．** 手順3の設計レビューでは元のローカルディレクトリを読み取り対象にしているため，そのパスのまま編集に入ると取り違える．元を編集すると，clone先には変更が無いまま空のコミット・PRになり，かつ元のローカルディレクトリに意図しない変更が残る．

### 4-3. コミット・push・PR作成

`for-pynthesis-skills`自身の場合

```
git add <変更したファイル>
git commit -m "<コミットメッセージ>"
git push -u origin HEAD
gh pr create --repo tt-and-tk/for-pynthesis-skills --title "<タイトル>" --body "<本文>" [--draft]
```

push先は，ブランチ名を書かず`HEAD`で現在のブランチを指す(`EnterWorktree`が作るブランチ名は`name`と一致しないため，名前を書くと存在しない別のブランチを新規に作ってしまう)．cloneしたリポジトリ側は自分で`git checkout -b`したブランチなので，名前をそのまま書いてよい．

それ以外のリポジトリの場合

```
git -C <cloneしたディレクトリの絶対パス> add <変更したファイル>
git -C <cloneしたディレクトリの絶対パス> commit -m "<コミットメッセージ>"
git -C <cloneしたディレクトリの絶対パス> push -u origin fix/issue-<番号>-<内容を表す短い語句>
gh pr create --repo tt-and-tk/<リポジトリ名> --head fix/issue-<番号>-<内容を表す短い語句> --title "<タイトル>" --body "<本文>" [--draft]
```

PRの`--body`にcloseキーワード(`Closes tt-and-tk/for-pynthesis-skills#番号`)またはリンクのみ(`Related to tt-and-tk/for-pynthesis-skills#番号`)を含める．closeキーワードは`for-pynthesis-skills`のPRにのみ付与する(issueは常にこのリポジトリに存在するため)．それ以外のリポジトリのPRは`Related to`のみを記載する．`--draft`はcloseキーワードを持つPRにのみ付ける．

### 4-4. 自動レビューループ

進め方は`issue-resolve`スキルの`SKILL.md`にある「自動レビューループ」の節に従う(以降，参照先と呼ぶ)．観点・実施条件の表・レビュー依頼文言の作り方・指摘への対応と記録は，すべてそちらを唯一の出典とする．本スキルでは次の点だけが異なる．

- ハードウェア記述レビューは行わない．本スキルが扱うのは複数プロジェクトに横断的に影響する修正であり，特定のハードウェアプロジェクトに閉じた変更は`issue-resolve`スキルの対象である
- `<owner>`は常に`tt-and-tk`である
- 全体レビューを1回だけ実施するという規定は，対象リポジトリごとに1回の意味である．複数のリポジトリを扱う場合，リポジトリごとに1回ずつ実施する
- レビュー結果の修正がまだ4-1〜4-3を行っていない別リポジトリにも及ぶ場合，参照先の「同じissueに対応する設定のブランチを切ってから対応する」は適用しない．本スキルはこのセッション内で串刺し編集ができるため，そのリポジトリについても4-1〜4-5を実行して対応する

### 4-5. 人間レビューへの対応

Draft解除はユーザーが行う．コメントを取得し，指摘があれば修正してコミット・pushする(cloneで作業しているリポジトリについては4-1の規定に従い`git -C <絶対パス>`形式で実行する)．インラインのレビューコメントとPR全体へのコメントは別に取得するため，以下は両方実行する．

```
gh api --paginate repos/tt-and-tk/<リポジトリ名>/pulls/<PR番号>/comments
gh api --paginate repos/tt-and-tk/<リポジトリ名>/issues/<PR番号>/comments
```

指摘一つずつについて，該当コメントへの返信で対応内容を伝える(必須)．インラインのレビューコメントにはスレッド返信，PR全体へのコメントには通常のコメントで返信するため，以下は該当する側のみ実行する．自動レビューが投稿するこれらのコメントは，人間の投稿と区別できるよう，`GH_TOKEN`環境変数でbotアカウントのトークン(`~/.gh-bot-token`)を明示してその1コマンドの実行時だけ切り替える(コミット・push・PR作成には適用せず，従来どおりの既定認証(人間のアカウント)を使う)．

```
GH_TOKEN=$(cat ~/.gh-bot-token) gh api repos/tt-and-tk/<リポジトリ名>/pulls/<PR番号>/comments/<コメントID>/replies -f body="<対応内容>"
GH_TOKEN=$(cat ~/.gh-bot-token) gh pr comment <PR番号> --repo tt-and-tk/<リポジトリ名> --body "<対応内容>"
```

対応後は4-4の自動レビューを再実行する(どの観点をどれだけ回すかは4-4の参照先が定める実施条件に従う)．

## 5. マージ

マージはユーザー自身が行う．

## 6. マージ後の後始末

マージ完了の報告を受けたら，issueがクローズされたことを確認する．後始末は，`for-pynthesis-skills`自身は`ExitWorktree`(`remove`)，それ以外は`rm -rf <cloneしたディレクトリの絶対パス>`．**両方を同一セッションで使った場合，`ExitWorktree`を先に実行する．** 4-1の順序どおり他リポジトリのcloneが`for-pynthesis-skills`自身のworktree配下にネストしていれば，`ExitWorktree`でworktreeごと削除されるため，その場合の個別の`rm -rf`は不要になる(対象が既に存在せず空振りになる)．

`for-pynthesis-skills`自身については，`ExitWorktree`実行後に元のローカルリポジトリでマージされた内容を反映するため，以下を実行する．

```
git pull
```

cloneで作業した各リポジトリについては，cloneを削除しただけではマージされた内容が本体のローカルクローンに反映されない．手順3で`--add-dir`に指定した，各リポジトリの既存のローカルディレクトリに対して以下を実行し，最新化する．

```
git -C <各リポジトリの既存のローカルディレクトリの絶対パス> pull
```

`for-pynthesis-skills`自身が対象リポジトリに含まれる場合，上記に加えて以下を実行し，インストール済みプラグインを最新化する(反映にはClaude Codeの再起動が必要なため，実行後はユーザーに再起動が必要な旨を伝える)．

```
claude plugin marketplace update for-pynthesis-skills
claude plugin update for-pynthesis-skills@for-pynthesis-skills
```

# レビュー指摘への向き合い方

AIレビュー(`claude -p`)・人間レビューのいずれであっても，指摘を鵜呑みにしてそのまま従うのではなく，**本当に対応すべきか，このまま変更しない方が正しいのではないかを都度考えてから，対応する・しないを判断する．**

- 対応する必要がないと判断した指摘は，対応しなくてよい(指摘に反論する，あるいは意図的に対応しない場合も認められる)．次のいずれかに当てはまる指摘が典型例である
  - 想定される利用状況からかけ離れた，極端に限定的な条件でしか問題にならない指摘
  - 指摘自体は妥当だが，わざわざ手を入れるほどの重要度がない指摘
  - 前提が事実と異なる指摘(誤読・古い情報に基づくもの)．該当箇所を実際に確認した上で，誤りを指摘して反論する
  - 今回の変更が原因ではなく，今回のissueのゴールからも外れる指摘(既存の別問題や将来の拡張)．ただし4-4のレビュアーは今回の変更範囲を知らないため，今回変更したファイル・記述そのものに対する指摘を，issueに書かれていないことだけを理由に却下しない．このうち起票済みでない既存不具合については，4-4の参照先が定める運用に従い，起票はせずユーザーへの報告対象として控えておく
  - ドキュメント・規定類の修正において，対応すると規定・手順が増え，得られる効果に対して運用の負担が見合わない指摘
- 対応した指摘は，PR上で指摘された箇所(ファイル・行)へのコメントとして対応内容を残し，あわせてコミットメッセージにも記録する．ここでのコメントはPR上のコメントであり，ソースコード中のコメント(`//`等)を書くことではない．人間レビューの指摘は4-5のスレッド返信がこれに当たる．AIレビュー(`claude -p`)の指摘には返信先のスレッドが存在しないため，指摘された箇所へのインラインコメントを新規に作成する
- 対応しなかった指摘(無視・反論)は，指摘された箇所へのコメントではなく，PR自体へのコメント(4-4のサマリーコメント)にその理由を残す(黙って無視しない)．ただし人間レビューのインラインコメントに対しては，4-5のスレッド返信で理由を返信する(必須)．4-5の指摘単位の個別スレッド返信と，4-4の観点呼び出し単位のサマリーコメントは粒度が異なる別の仕組みであり，どちらも既存のルールに従う
- 対応する・しないの判断の考え方は，手順3(PR作成前の設計レビュー)の指摘にも適用する．記録先の規定のみPR作成後(4-4・4-5)の指摘に適用し，手順3で反論する場合は同項の運用(次のレビュー依頼プロンプトに含める)に従う

# 注意

- 1issueに対して複数のPRがある場合，closeキーワードを持つPRは1つだけにする
- 影響リポジトリが不明な場合は，ユーザーに確認する
